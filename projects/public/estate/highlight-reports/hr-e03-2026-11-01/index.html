Status summary

S1 · proposed WP-E5 · AMBER

WP-E5 scopes an architecture in which each app has an explicit local data boundary and data-only catalogue changes refresh subscribed app caches without a full site rebuild. The current site already has a central SQLite catalogue, GraphQL browser resolver, graph edges, generated SQLite slices and generated per-app JSON views. The gap is that those views are currently build outputs, not independently refreshed from an event feed. No production event publisher, queue consumer or fleet of app databases is claimed complete.

Key issues and risks

6 open design risks
  • App-local SQLite/JSON views are build-time products; data-only changes still depend on static build publication.
  • The main build allows some view generation failures to fall back to old static pages; cache freshness can become stale unless reported and gated.
  • Per-app D1 databases may be appropriate for relational or writable apps, but a database for every area may add cost and operational complexity. Use JSON/R2 or static SQLite where sufficient.
  • Event delivery must handle duplicates, ordering, retries, dead letters, replay and a full reconciliation path.
  • GraphRAG may surface relevant context but must not collapse neutral source description, verbatim transcript and interpretation or convert retrieval relevance into evidential weight.
  • Release retention must never remove an active production alias or the newest three successful builds. Skipped preview records must be treated separately from completed deployments.

Lessons report (if appropriate)

Prompt-only standards are insufficient

Agent instructions need to be backed by machine-enforced architecture contracts, ADRs, a golden-path template, protected branch/release rules, CI checks and independent verification. A successful build is not proof that every data view is current or that an app is independently extractable.
