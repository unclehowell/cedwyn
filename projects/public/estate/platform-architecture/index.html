Make Cedwyn modular: one authoritative evidence/artifact catalogue, independently bounded webapps, and data refreshes that do not require source-code changes or a full Cloudflare Pages rebuild.

1. Purpose and intended outcome

Data change ≠ code deployment

Each Cedwyn webapp should own a small, explicit data boundary: its frontend, worker/API where needed, schema and migrations, relevance rules, local cache/database, tests and versioned interface. It should retrieve only the central catalogue records relevant to its purpose.

When a new artifact or revision enters the central catalogue, the catalogue should publish a versioned change event. Relevant app caches should update independently, and each frontend should read a simple versioned JSON view (with GraphQL available for richer queries and agent use). A data-only change should not require changing app source code, rebuilding every app or redeploying the static website.

Every app should be separable into its own deployable product without first untangling hidden dependencies on unrelated webapps.

3. Proposed architecture

Central catalogue → event feed → app cache → frontend JSON/GraphQL
  1. Canonical catalogue. Retain one authoritative catalogue initially. Give each artifact a stable catalogue ID and immutable revision/hash. Keep source bytes, neutral description, verbatim transcript/transcription status, interpretation and graph observations as separate linked records.
  2. Change feed. On an accepted catalogue change, publish an append-only event and a versioned manifest with a monotonic sequence/cursor, stable artifact ID, revision/hash, changed fields and structured relevance keys (entities, dates, theme/area, parcel, source type and graph relations). Keep an outbox/replay path.
  3. Durable event transport. Evaluate R2 JSON manifests/change objects with R2 event notifications into a Cloudflare Queue. A common sync Worker consumes events with idempotency, retry, dead-letter handling, cursor checks and full-resync support.
  4. Per-app relevance rules. Each app declares its own selector/subscription contract. Deterministic keys decide mandatory inclusion. GraphRAG/vector retrieval may suggest additional context, but each inclusion reason must be inspectable and linked to source catalogue IDs.
  5. App-local store. Use a D1 database for apps needing relational queries, app-specific writes or durable state; use a versioned R2 JSON snapshot or static SQLite view for apps that are predominantly read-only. Do not provision one D1 database per every public area before checking app needs, account plan, usage and cost.
  6. Data plane. Publish a simple /{app}/_db/current.json (or a documented app API route) containing app/schema version, catalogue cursor, generated time, freshness state and content. Use ETag/If-None-Match and 304 responses; versioned immutable snapshots should support rollback and replay.
  7. Query plane. Keep GraphQL for flexible cross-entity and agent queries; use predictable JSON/SQLite read models for ordinary page rendering. GraphRAG should use the existing graph and, where warranted, vector retrieval, while preserving source citations and an explicit distinction between retrieval relevance and evidential weight.
  8. Independent extraction. An app must be portable with its frontend, worker/API, data schema/migrations, configuration, subscription contract, tests and release history. Shared services are consumed through explicit versioned contracts, not accidental imports across app folders.

Candidate standard app layout (adapt to the existing repository where this reduces migration cost):

apps/{app-id}/
  app.manifest.json
  subscriptions.json
  schema.sql
  migrations/
  worker/
  web/
  tests/
  CHANGELOG.md
  README.md

Do not create a second competing registry. Reconcile the proposed manifest with themes.json, data/site-areas.json and the existing section/theme registry, then choose one authoritative app identity and route mapping.

Cloudflare's D1 documentation supports separate databases for projects/tenants, but the final number of databases and any paid tier must be justified against real app boundaries and account limits. D1 Time Travel, backups, migration discipline and restore tests need to be included in the design.

5. Evidence and interpretation contract

Preserve lineage and separate source from inference

Each central record should distinguish:

  • Artifact/source: immutable bytes or preserved copy, stable catalogue ID, hash, creator/holder, date, provenance and access limitations.
  • Neutral description: what the item is and what it visibly or textually contains; do not smuggle interpretation into the description.
  • Transcript/transcription: verbatim text, method (manual/OCR/ASR), verification state, language and page/time references. Do not silently correct or paraphrase the transcript.
  • Interpretation: a separate best-effort reading with author/model, prompt/rules version, date, relevant wider-context references, reasoning limitations and links to the source artefacts.
  • Observation/graph edge: a testable proposition or relationship, its supporting and countervailing references, scope, confidence and falsification questions.

GraphRAG can surface a wider context and help explain why an artefact may matter. Its relevance score is not proof of authenticity, intent, misconduct, title, legal effect or a court finding. Uncertainty must remain visible.

6. Engineering guardrails and anti-slop controls

Governance enforced by code, not prompt prose alone

The umbrella is engineering and architecture governance. The enforceable mechanisms are architecture contracts, architecture decision records (ADRs), a golden-path app template, policy-as-code and architecture fitness functions in CI. Agent instructions are supporting controls, not the only control.

  • Architecture contract: repo-level ARCHITECTURE.md, AGENTS.md and CONTRIBUTING.md state app boundaries, data ownership, event/JSON/GraphQL contracts, release process and forbidden shortcuts.
  • ADRs: record why D1, R2, Queue, GraphQL, GraphRAG and app boundaries are chosen; document rejected alternatives and cost/risk.
  • Golden path: scaffold a webapp with manifest, subscriptions, cache schema/migrations, Worker, frontend, tests, README and changelog.
  • CI fitness functions: enforce app import boundaries, schema validation, stable IDs/hashes, source/transcript/interpretation separation, provenance links, GraphQL compatibility, cursor/idempotency/replay tests, migration compatibility, stale-cache detection, privacy/editorial/theme/mobile checks, SemVer and changelog completeness.
  • Branch/release governance: protected main/shared branches where available, scoped feature branches, CODEOWNERS, required checks, PR review and immutable annotated SemVer tags.
  • Failure behaviour: do not turn required DB/view/cache generation failures into warnings that silently publish stale outputs. Explicitly label stale state and stop release when a required acceptance gate fails.

7. Release and retention policy

Per-branch SemVer; last-three retention; never delete active production
  • Every published branch/webapp change passes a PR and becomes a genuine GitHub Release with an annotated SemVer tag pointing at the exact release commit. target_commitish in a release record is not a substitute for checking the tag object's target SHA.
  • Every branch/webapp keeps a .version (or documented version file) and CHANGELOG.md using Keep a Changelog sections. MAJOR = incompatible contract; MINOR = backward-compatible feature; PATCH = backward-compatible fix.
  • Retain the newest three published semantic releases per app/branch. Older release records and their corresponding tags may be removed only after dry-run inventory, confirmation that tag references are not used by a deployment, and an auditable deletion log. Do not rewrite or delete underlying Git commit history.
  • Retain the three newest successful Cloudflare deployments per project/environment and always preserve the active production deployment and any deployment with a live custom-domain alias. Count successful production builds, not skipped preview records. Treat skipped previews as a separate class with their own retention/reporting policy.
  • Retention jobs must default to dry-run, use an explicit project allowlist, emit before/after JSON and support rollback where Cloudflare permits. Never delete a Pages project, a custom domain, an active alias or an artefact still referenced by a live app.

In this audit, the Cedwyn Pages API returned 447 production deployment records and 2,107 skipped preview records. This page does not claim that the records have been purged; safe retention automation remains a deliverable.

8. Delivery sequence and team boundaries

Shared platform once; bounded app work in parallel
  1. Architecture lead: map the central DB, GraphQL, graph, static slices, per-app JSON views, current Workers/D1, R2 objects, Page projects and release workflows; produce an ADR-backed target design and migration map.
  2. Release/DevOps: implement generic branch release and retention workflows with dry-run, annotated tags, last-three protection and changelog validation.
  3. Catalogue/data: define artifact revision, manifest and append-only change-event schemas, plus an outbox/replay/full-resync mechanism.
  4. Sync/runtime: implement the Queue consumer, subscription evaluator, D1/JSON snapshot updater, idempotency, retries, dead-letter visibility, freshness and cursor APIs.
  5. App work packages: one per registered public area/webapp, starting with HubSpot, Chess, Dartboard, That Old Chestnut, Wiki/Research and Map Room. Generate the complete inventory from data/site-areas.json; do not assume the six pilots are the whole estate.
  6. Independent assurance: separate builder, challenger and verifier. The builder does not self-approve. Verify live behaviour, data lineage, cache freshness, mobile/theme, permissions, spend and retention safety.

Coordinate through Hive and Cedwyn Academy. Each app team owns only its app boundary and local cache contract. Changes to shared runtime/catalogue contracts go through one site-wide PR with an explicit migration/compatibility plan.

9. Acceptance tests

Prove data refresh without a Pages deployment
  • Insert a new artifact revision into the central catalogue without changing app source code and without triggering a full Pages rebuild.
  • Only subscribed app caches receive the event; unrelated app versions/cursors remain unchanged.
  • The frontend sees the new record through its current JSON endpoint and ETag/304 behaviour; cache cursor and freshness are inspectable.
  • GraphQL and GraphRAG results resolve to the same stable catalogue ID and cite source artefacts; transcript and interpretation remain separate.
  • Duplicate delivery is harmless; failures retry; dead-letter state is visible; replay and full resync restore the same cache state.
  • At least one pilot app can be extracted with its own frontend, Worker/API, cache DB, migrations, subscription contract, tests and release history.
  • Release tests verify SemVer, changelog, annotated tag target SHA, genuine Release record and last-three retention.
  • Cloudflare retention dry-run preserves the current production alias and three latest successful production builds, classifying skipped preview records separately.
  • Existing evidence hierarchy, privacy, editorial, accessibility, navigation, dark/light theme, mobile and full build tests continue to pass.

10. Risks, constraints and decision gates

No premature provisioning or destructive cleanup
RiskControl / next gate
Too many D1 databases increase account complexity and cost.Classify each app's read/write/query needs; use R2 JSON or SQLite snapshots where sufficient; provision only pilot DBs after plan/cost check.
Out-of-order/duplicate events leave a cache stale or inconsistent.Monotonic sequence cursor, idempotency key, transaction/batch writes, retries, DLQ, replay and reconciliation jobs.
GraphRAG returns plausible but unsupported interpretations.Evidence links mandatory; neutral description, transcript and interpretation remain separate; record counterevidence and limits.
App caches drift from the catalogue without anyone noticing.Published freshness/cursor state, periodic audit reconciliation, stale indicators and hard CI gates for required build-time products.
Release cleanup deletes a required tag/build or breaks production alias.Dry-run by app/project/environment, explicit allowlist, retain last three successful releases/builds, preserve active aliases, auditable deletion log.
Concurrent agents collide on shared app registry or common runtime.One app owner per work package; explicit file ownership; site-wide PR for shared contracts; serial registry integration and independent reviewer.

Decision gates: first accept the architecture and ADRs; next approve one read-only pilot; then review correctness/cost/failure recovery; only then roll out per-app DBs or enable automated cleanup. No expenditure, destructive retention, external contact or public statement is authorised by this proposal.
