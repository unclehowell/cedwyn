Consolidate the BucklerFamily Estate webapps under cedwyn.bucklerfamily.estate/, while keeping each area modular enough to version, deploy, roll back, or extract independently. Keep the evidence catalogue as the shared reference layer. This is an enabling work package within the existing programme, not a sixth programme objective.

Required outcome

One site, many independently managed webapps
  • Every ordinary legacy app URL maps to a canonical path: for example, fcg.bucklerfamily.estate/case/7 → cedwyn.bucklerfamily.estate/fcg/case/7. Keep the path and query unless that app's contract requires a documented exception.
  • Keep service endpoints and media distinct from pages. MCP/WebMCP, API paths, downloads, video/image/PDF hosts, archive originals and agent routes need their own tests and explicit routing rules.
  • Each webapp has an app manifest, source reference, semantic version, change log, data-schema contract, health checks and a known rollback reference.
  • Use stable catalogue artifact IDs for shared records and provenance. App-specific databases may hold app-owned state or derived projections; they must not become competing authorities for the same evidence.
  • Maintain separate views: Research/Legal Wiki, land/title-chain infographic, History & Heritage, Gallery, and a new Architecture reconstruction area for the Argentina project.

Architecture decisions to establish

Keep apps replaceable
  1. App boundary: one stable path, source/build reference, manifest and release history per app. Removing one app must leave navigation and other app paths working.
  2. Catalogue boundary: the catalogue owns canonical evidence, provenance, citations and stable IDs. The existing static SQLite build remains the distribution format until an API-backed read/sync design is accepted.
  3. App database boundary: separate D1 databases are suitable for app-owned writable state where they already exist. Do not copy the evidence catalogue into each app as another authority.
  4. Extraction path: each app should have a documented route and schema contract so a popular area can move to a separate site later without rewriting the entire website.
  5. Reconstruction certainty: architecture records must label source-measured dimensions, inferred geometry and illustrative hypotheses separately; no inferred dimension should be presented as a measured fact.

Risks and controls

No regression takes precedence over speed
  • Existing service behaviour changes: never redirect APIs, agent endpoints or media hosts using the generic page rule. Test each declared endpoint independently.
  • Ambiguous source mapping: do not invent a DNS record or assign a legacy host to an app until its source and destination are confirmed.
  • Release drift: preserve historical tags; do not fabricate prior versions. Resolve the 35/38/44 counts and 1.0.2/1.1.1 version mismatch first.
  • Deployment coupling: changes under the site build tools can trigger a full production rebuild on merge. Keep the audit PR as a draft and validate any production build separately.
  • Storage drift: inspect schema and binding metadata before migration; no application data rows were read in this audit.

Stop before production changes if a required route fails, an endpoint is shadowed, content parity regresses, a privacy/security check fails, or the previous production deployment cannot be restored.
